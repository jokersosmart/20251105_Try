# 功能規格書：社群留言爬蟲工具

**Feature Branch**: `001-social-comment-scraper`  
**Created**: 2025-11-19  
**Status**: Draft  
**Input**: 線上社群留言爬蟲工具，支援 Instagram 和 Facebook 公開貼文留言擷取，提供線上編輯和 Excel 匯出功能

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 爬取單一貼文留言 (Priority: P1) 🎯 MVP

操作人員需要快速收集特定社群貼文的所有留言資料，以便進行客戶意見分析。使用者只需貼上貼文網址，系統即可自動擷取所有公開留言，包括留言者資訊、留言內容和時間戳記。

**為何優先**: 這是整個工具的核心價值，沒有這個功能就無法進行任何後續資料處理。這個功能單獨就能提供即時的資料收集價值，滿足基本的資料蒐集需求。

**Independent Test**: 可透過提供一個 Instagram 或 Facebook 公開貼文網址，驗證系統能完整擷取所有留言並顯示在介面上，即代表功能完整可用。

**Acceptance Scenarios**:

1. **Given** 使用者在首頁，**When** 貼上 Instagram 公開貼文網址並點擊「開始爬取」，**Then** 系統顯示進度指示器並在完成後列出所有留言（包含留言者名稱、頭像連結、留言內容、留言時間）
2. **Given** 使用者在首頁，**When** 貼上 Facebook 粉絲專頁公開貼文網址並點擊「開始爬取」，**Then** 系統顯示進度指示器並在完成後列出所有留言（包含留言者名稱、留言內容、留言時間、按讚數）
3. **Given** 使用者輸入無效的網址格式，**When** 點擊「開始爬取」，**Then** 系統顯示明確的錯誤訊息「網址格式不正確，請輸入有效的 Instagram 或 Facebook 貼文網址」
4. **Given** 使用者輸入私人貼文網址，**When** 點擊「開始爬取」，**Then** 系統顯示訊息「此貼文為私人貼文或無法存取，請確認貼文為公開狀態」
5. **Given** 系統正在爬取資料，**When** 爬取過程中發生網路錯誤，**Then** 系統顯示「連線中斷，已保存部分資料」並顯示已擷取的留言數量

---

### User Story 2 - 線上編輯留言資料 (Priority: P2)

操作人員在爬取留言後，需要對資料進行清理、分類或標記，例如標示重要留言、刪除無關內容、新增分類標籤等，以便後續分析使用。

**為何優先**: 原始爬取的資料通常包含雜訊或需要分類，線上編輯功能讓使用者能立即處理資料，避免需要匯出後再用其他工具編輯。這顯著提升工作效率。

**Independent Test**: 在完成 User Story 1 後，使用者可以對已爬取的留言進行編輯（修改內容、刪除列、新增標籤欄位），並確認編輯結果即時反映在介面上。

**Acceptance Scenarios**:

1. **Given** 已爬取的留言資料顯示在表格中，**When** 使用者點擊任一留言的「編輯」按鈕並修改留言內容，**Then** 系統即時更新該列資料並顯示「已儲存」提示
2. **Given** 表格中顯示多筆留言，**When** 使用者勾選特定留言列並點擊「刪除選取項目」，**Then** 系統顯示確認對話框「確定要刪除 N 筆留言？」，確認後移除選取的留言
3. **Given** 使用者在表格中，**When** 點擊「新增欄位」並輸入欄位名稱「客戶類型」，**Then** 系統在表格最右側新增一個可編輯的欄位，所有留言該欄位預設為空白
4. **Given** 使用者已對留言進行多次編輯，**When** 不小心誤刪重要留言，**Then** 可以點擊「復原」按鈕恢復最近一次的操作（支援至多 10 步復原）
5. **Given** 表格中有大量留言資料，**When** 使用者在搜尋框輸入關鍵字，**Then** 表格即時篩選並只顯示內容包含該關鍵字的留言

---

### User Story 3 - 匯出為 Excel 檔案 (Priority: P3)

操作人員完成資料清理後，需要將最終資料匯出為 Excel 檔案，以便在本地進行進階分析、製作報表，或與團隊分享資料。

**為何優先**: Excel 是商業環境中最通用的資料分析工具，匯出功能讓使用者能將資料整合到現有的工作流程中，大幅提升工具的實用性。

**Independent Test**: 使用者可以點擊「匯出 Excel」按鈕，下載包含所有留言資料（包括編輯後的內容和自訂欄位）的 .xlsx 檔案，並能在 Excel 中正常開啟查看。

**Acceptance Scenarios**:

1. **Given** 表格中有已爬取和編輯的留言資料，**When** 使用者點擊「匯出 Excel」按鈕，**Then** 瀏覽器自動下載一個命名為「留言資料_日期時間.xlsx」的檔案
2. **Given** 下載的 Excel 檔案，**When** 使用者在 Excel 中開啟，**Then** 所有欄位（留言者、內容、時間、自訂欄位等）正確對應，中文內容顯示正常無亂碼
3. **Given** 表格中有超過 1000 筆留言，**When** 執行匯出操作，**Then** 系統顯示「正在產生檔案...」進度提示，並在 10 秒內完成下載
4. **Given** 使用者已套用篩選條件（例如只顯示特定關鍵字的留言），**When** 點擊「匯出 Excel」，**Then** 系統詢問「要匯出全部資料還是僅匯出篩選後的資料？」並根據選擇執行
5. **Given** 匯出過程中發生錯誤，**When** 系統無法產生檔案，**Then** 顯示明確訊息「匯出失敗：資料量過大或系統繁忙，請稍後再試」

---

### User Story 4 - 批次處理多個貼文 (Priority: P4)

操作人員需要定期監測多個粉絲專頁或帳號的留言，希望能一次輸入多個貼文網址進行批次爬取，避免逐一手動處理。

**為何優先**: 這是效率提升功能，對於需要定期監測多個來源的使用者非常實用，但不影響基本功能的使用。屬於錦上添花的功能。

**Independent Test**: 使用者可以在「批次模式」中貼上多個貼文網址（每行一個），系統依序或並行爬取，最終將所有留言整合在同一個表格中，並標註來源貼文。

**Acceptance Scenarios**:

1. **Given** 使用者在首頁點擊「切換到批次模式」，**When** 在文字框中貼上 5 個不同的貼文網址（每行一個）並點擊「開始批次爬取」，**Then** 系統顯示進度「正在處理 1/5...」並逐一爬取
2. **Given** 批次爬取完成，**When** 查看結果表格，**Then** 所有留言資料整合在同一表格中，且每筆留言都有「來源貼文」欄位標註其原始網址
3. **Given** 批次模式中輸入 10 個網址，其中 2 個網址無效，**When** 執行爬取，**Then** 系統顯示「2 個網址失敗：[列出失敗的網址及原因]，其餘 8 個已成功爬取」
4. **Given** 使用者上傳一個包含 20 個貼文網址的 .txt 或 .csv 檔案，**When** 點擊「開始批次爬取」，**Then** 系統讀取檔案中的所有網址並開始批次處理
5. **Given** 批次爬取正在進行中，**When** 使用者發現其中一個網址錯誤，**Then** 可以點擊「取消批次作業」中止所有進行中的任務

---

### Edge Cases

- **網路連線問題與自動續傳**: 爬取過程中若發生網路中斷，系統自動將已擷取的留言資料和爬取進度狀態保存到 IndexedDB。當使用者重新開啟應用程式或網路恢復時，系統偵測到未完成的爬取任務，顯示提示訊息「偵測到未完成的爬取任務（貼文：[網址]，已擷取 X 則留言），要繼續爬取嗎？」，讓使用者選擇「繼續」或「放棄並清除」。選擇繼續時，系統從上次中斷的位置繼續爬取，避免重複擷取相同留言
- **平台限制**: 當 Instagram/Facebook API 達到速率限制（rate limit）時，系統應顯示「平台暫時限制存取，請等待 X 分鐘後再試」並記錄重試時間
- **大量留言處理**: 當貼文有超過 10,000 則留言時，系統應詢問使用者「此貼文有大量留言，可能需要較長時間，是否繼續？」並在處理時分批顯示進度
- **過期或刪除的貼文**: 當貼文已被刪除或連結失效時，系統應顯示「貼文不存在或已被移除」
- **留言更新**: 使用者可能需要重新爬取已爬過的貼文以獲取新留言，系統應提供「更新留言」選項，並標示新增的留言
- **特殊字元和表情符號**: 留言內容包含 emoji、特殊符號時，應正確顯示和匯出，不產生亂碼
- **並行爬取限制**: 批次模式同時爬取多個貼文時，應限制並行數量（建議不超過 3 個）以避免觸發平台的反爬蟲機制
- **瀏覽器相容性**: 應支援主流瀏覽器（Chrome、Edge、Firefox、Safari）並在不支援的瀏覽器顯示提示訊息
- **儲存配額管理**: 當 IndexedDB 使用量達到 80% 配額時，系統顯示警告橫幅「儲存空間即將不足（已使用 X MB / 總共 Y MB），建議清理舊資料」。點擊警告開啟清理工具，顯示所有已爬取的貼文列表（按日期排序），使用者可勾選並刪除不需要的貼文資料。當配額達到 95% 時，禁止新的爬取操作並強制要求清理
- **後端代理服務異常**: 當後端 API 代理服務無法連線或回應錯誤時，系統顯示「服務暫時無法使用，請稍後再試」並記錄錯誤日誌。提供「檢查服務狀態」連結供使用者確認系統狀態

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統必須接受 Instagram 和 Facebook 公開貼文的完整網址作為輸入
- **FR-002**: 系統必須驗證輸入的網址格式，並在格式不正確時顯示明確的錯誤訊息
- **FR-003**: 系統必須能擷取公開貼文的所有留言，包括留言者名稱、留言內容、留言時間、互動數據（按讚數、回覆數）
- **FR-004**: 系統必須在爬取過程中顯示即時進度指示器（例如：已擷取 X 則留言）
- **FR-005**: 系統必須將爬取的留言資料以表格形式呈現，並提供排序功能（按時間、按讚數等）
- **FR-006**: 使用者必須能在線上編輯表格中的任何儲存格內容
- **FR-007**: 使用者必須能勾選並刪除多筆留言記錄
- **FR-008**: 系統必須支援新增自訂欄位（例如：客戶類型、回應狀態、優先等級），所有自訂欄位均為純文字類型，使用者可在欄位中輸入任何文字內容
- **FR-009**: 系統必須提供搜尋和篩選功能，讓使用者快速找到特定留言
- **FR-010**: 系統必須支援復原（Undo）功能，至少保留最近 10 次操作記錄
- **FR-011**: 系統必須能將表格資料匯出為 .xlsx 格式的 Excel 檔案
- **FR-012**: 匯出的 Excel 檔案必須包含所有可見欄位（原始欄位和自訂欄位），且中文內容無亂碼
- **FR-013**: 系統必須支援批次模式，允許使用者一次輸入多個貼文網址進行爬取
- **FR-014**: 批次爬取時，系統必須標註每筆留言的來源貼文網址
- **FR-015**: 系統必須處理錯誤情況（無效網址、私人貼文、已刪除貼文、網路錯誤）並顯示友善的錯誤訊息
- **FR-016**: 系統必須在爬取過程中遇到平台速率限制時，自動暫停並通知使用者預計等待時間
- **FR-017**: 所有 UI 文字、按鈕標籤、錯誤訊息必須使用繁體中文
- **FR-018**: 系統必須記錄使用者最近的操作（例如：最近爬取的貼文），方便快速重新存取
- **FR-019**: 系統必須實作自動續傳機制，當爬取過程中斷時自動保存進度（已擷取的留言和爬取狀態）。重新開啟應用程式時偵測未完成任務並提示使用者選擇繼續或放棄，繼續時從中斷處恢復避免重複爬取
- **FR-020**: 系統必須監控 IndexedDB 儲存配額使用量，當達到 80% 時顯示警告訊息「儲存空間即將不足，建議清理舊資料」，並提供清理工具介面讓使用者查看和選擇性刪除已爬取的貼文資料
- **FR-021**: 系統必須將所有留言時間戳記（來自 API 的 UTC 時間）轉換為使用者本地時區（台灣 GMT+8）進行顯示，格式為「YYYY-MM-DD HH:mm」，Excel 匯出時保持相同格式
- **FR-022**: 前端必須透過後端 API 代理層呼叫 Instagram 和 Facebook API，不得在前端程式碼中直接包含 App Access Token。所有 API 請求必須經過後端驗證和速率限制檢查

### Key Entities

- **貼文 (Post)**: 代表 Instagram 或 Facebook 上的單一貼文，屬性包括：貼文網址、平台類型（Instagram/Facebook）、貼文標題、發文者、發文時間、貼文 ID
- **留言 (Comment)**: 代表貼文下的單一留言，屬性包括：留言 ID、留言者名稱、留言者頭像連結、留言內容、留言時間、按讚數、回覆數、來源貼文（關聯到 Post）
- **使用者工作階段 (User Session)**: 代表單次使用過程，屬性包括：工作階段 ID、建立時間、已爬取的貼文列表、當前資料狀態（編輯中的留言表格）、IndexedDB 配額使用量
- **爬取狀態 (Scraping State)**: 記錄進行中或中斷的爬取任務，屬性包括：貼文網址、開始時間、當前進度（已擷取留言數量）、最後更新時間、狀態（進行中/已暫停/已完成）、最後成功的 API 分頁游標（用於續傳）。此實體支援自動續傳機制
- **自訂欄位 (Custom Field)**: 使用者新增的額外欄位，屬性包括：欄位名稱、欄位值（純文字）。所有自訂欄位均為文字類型，提供最大彈性且易於使用，使用者可自由輸入任何內容進行分類或標記
- **操作歷史 (Operation History)**: 記錄使用者的編輯操作以支援復原功能，屬性包括：操作類型（編輯/刪除/新增）、操作時間、受影響的資料、前後狀態
- **儲存配額狀態 (Storage Quota Status)**: 追蹤 IndexedDB 使用量，屬性包括：已使用空間、總配額、使用百分比、最後檢查時間。用於觸發 80% 警告和清理工具顯示

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者從貼上網址到看到第一筆留言資料的時間在 5 秒內（針對少於 100 則留言的貼文）
- **SC-002**: 系統能成功爬取並顯示至少 90% 的公開留言（部分留言因平台限制可能無法取得）
- **SC-003**: 90% 的使用者能在 3 分鐘內完成首次爬取任務（包括貼上網址、執行爬取、查看結果）
- **SC-004**: 匯出的 Excel 檔案在常見的 Excel 軟體（Microsoft Excel、Google Sheets、WPS）中開啟時，100% 的中文內容正確顯示無亂碼
- **SC-005**: 系統在處理包含 1,000 則留言的貼文時，頁面載入時間不超過 3 秒，編輯操作回應時間不超過 500 毫秒
- **SC-006**: 批次模式處理 10 個貼文的總時間不超過 5 分鐘（假設每個貼文平均 200 則留言）
- **SC-007**: 使用者首次使用時，95% 能在無需查看說明文件的情況下完成基本爬取和匯出操作（介面直覺性測試）
- **SC-008**: 錯誤情況發生時，100% 的錯誤訊息必須清楚說明問題原因和建議解決方式（無「系統錯誤」等模糊訊息）
- **SC-009**: 當 IndexedDB 配額達到 80% 時，系統必須在 3 秒內顯示警告訊息，且清理工具能讓使用者在 1 分鐘內完成舊資料刪除操作
- **SC-010**: 所有留言時間戳記在介面和 Excel 匯出中顯示為本地時間（台灣時區），且格式一致無誤差

### Constitution Compliance *(mandatory)*

**Per Constitution Principles**:

- **Code Quality**: 
  - 程式碼覆蓋率目標：80% 最低要求，爬蟲核心邏輯和資料處理模組達到 100%
  - 所有程式碼必須通過 ESLint/Prettier 檢查
  - 複雜度 (cyclomatic complexity) 不得超過 10

- **Testing Standards**: 
  - 必須包含的測試類型：
    - **契約測試 (Contract Tests)**: 驗證與 Instagram/Facebook API 的互動
    - **整合測試 (Integration Tests)**: 驗證端到端的爬取、編輯、匯出流程
    - **單元測試 (Unit Tests)**: 驗證網址解析、資料轉換、錯誤處理等獨立模組
    - **效能測試 (Performance Tests)**: 驗證大量留言（1000+ 則）的處理效能

- **UX Consistency**: 
  - 使用者互動回應時間：<100ms（按鈕點擊、輸入回饋）
  - 顯示載入指示器：所有超過 300ms 的操作（爬取、匯出）
  - WCAG 2.1 AA 無障礙合規：支援鍵盤導航、螢幕閱讀器、高對比模式
  - 錯誤訊息：必須使用繁體中文、說明問題原因、提供解決建議（例如「網址格式不正確，請確認為 https://www.instagram.com/p/... 或 https://www.facebook.com/... 格式」）

- **Performance Requirements**:
  - 頁面初次載入時間：<2 秒（3G 網路環境）
  - 爬取 API 回應時間：<3 秒啟動爬取程序，每 100 則留言更新一次進度（<500ms）
  - Excel 匯出時間：1000 則留言在 5 秒內完成檔案產生和下載
  - 前端 bundle 大小：<300KB (gzipped)，使用程式碼分割 (code splitting) 優化載入
  - 記憶體使用：處理 10,000 則留言時瀏覽器記憶體使用不超過 500MB

- **Documentation & Localization**:
  - ✅ 本規格書使用繁體中文撰寫
  - ✅ 所有使用者故事使用繁體中文
  - ✅ 所有 UI 文字必須使用繁體中文（按鈕、標籤、提示、錯誤訊息）
  - ✅ 錯誤訊息必須使用繁體中文並提供明確的指引

## 假設與限制

### 假設 (Assumptions)

1. **平台存取權限**: 系統使用 Instagram Graph API 和 Facebook Graph API 作為資料來源。假設開發團隊已申請並獲得必要的開發者權限和應用程式層級的 API 存取金鑰（App Access Token）。所有資料存取完全符合平台服務條款，確保合法合規
2. **系統架構**: 系統採用前端為主 + 輕量後端代理的混合架構。前端負責 UI 互動和資料展示，後端代理層（Serverless Functions 如 AWS Lambda、Vercel Functions）負責 API 呼叫和 Token 保護。此設計兼顧使用體驗和安全性
3. **認證機制**: 系統採用應用程式層級授權（App Access Token），使用者無需使用個人社群帳號登入或授權即可使用所有功能。API 金鑰安全地儲存在後端代理層，前端透過代理端點呼叫 API，確保 Token 不暴露於前端程式碼
4. **API 可用性**: 假設 Instagram 和 Facebook 的 Graph API 在專案開發和營運期間保持可用，且 API 的公開資料端點（public data endpoints）足以支援規格書定義的所有核心功能（公開貼文留言擷取、留言者資訊、互動數據等）
5. **使用者網路環境**: 假設使用者具備穩定的網路連線（至少 3G/4G 或寬頻），以支援即時 API 呼叫和資料處理
6. **瀏覽器支援**: 假設使用者使用現代瀏覽器（Chrome 90+, Edge 90+, Firefox 88+, Safari 14+），支援 IndexedDB、Fetch API、ES6+ 等現代 Web 標準
7. **資料儲存方式**: 系統採用瀏覽器端儲存架構，使用 IndexedDB 作為主要儲存機制（支援大量資料），localStorage 作為輔助（儲存使用者偏好設定）。資料保留在使用者本地裝置，預設保留 30 天或直到使用者手動清除。系統在 IndexedDB 使用量達到 80% 配額時顯示警告，並提供清理工具讓使用者選擇性刪除舊資料
8. **時間顯示標準**: 所有留言時間戳記統一轉換並顯示為使用者本地時區（台灣 GMT+8），提供最佳可讀性和分析便利性。Excel 匯出時也採用本地時間格式
9. **語言環境**: 假設目標使用者為繁體中文使用者，系統介面和錯誤訊息以繁體中文為主

### 限制 (Constraints)

1. **混合架構需求**: 系統採用前端 + 後端代理的混合架構，需要部署和維護輕量級的 Serverless 後端服務（如 AWS Lambda、Vercel Functions、Cloudflare Workers）。雖然後端邏輯簡單（僅作為 API 代理），但仍需考慮部署成本、監控和維護
2. **API 速率限制**: Instagram 和 Facebook Graph API 設有嚴格的速率限制（rate limiting）。由於採用應用程式層級授權，所有使用者共用同一組 API 配額。後端代理層必須實作適當的節流機制、排隊系統和配額監控，超過限制時須等待或提示使用者稍後再試
3. **僅限公開資料**: 使用應用程式層級授權（App Access Token）只能存取完全公開的貼文和留言資料，無法存取需要使用者個人授權才能取得的私人或受限內容
4. **API 功能限制**: 部分留言資料可能因 API 權限限制而無法取得（例如：私人留言、特定類型的互動數據）。系統能擷取的資料範圍受限於 API 提供的公開資料端點和欄位
5. **開發者審核要求**: 使用 Instagram 和 Facebook API 需通過平台的應用程式審核流程，可能需要提供商業使用說明和隱私政策文件
6. **後端服務可用性**: 系統依賴後端代理服務的可用性，若 Serverless 平台發生故障或達到服務限制，將影響 API 呼叫功能
7. **法律合規**: 系統必須遵守台灣個人資料保護法及相關社群平台的服務條款，擷取的資料僅供合法商業分析使用
8. **API 穩定性**: 若平台更新 API 版本或異動欄位結構，後端代理層和前端程式碼可能需要相應更新維護
9. **瀏覽器儲存配額**: IndexedDB 儲存空間受瀏覽器和裝置限制（通常數 GB），達到配額上限時系統功能受限。使用者需定期清理舊資料以保持系統可用
10. **匯出檔案大小**: Excel 檔案匯出受限於瀏覽器記憶體，建議單次匯出不超過 50,000 則留言（約 50MB）

### 建議的技術參考方向（僅供規劃階段參考）

此部分不構成規格要求，僅作為後續技術規劃的參考：

**系統架構**:
- **前端**: 單頁應用（SPA），負責 UI 互動、資料展示、本地儲存管理
- **後端代理層**: 輕量級 Serverless Functions（AWS Lambda / Vercel Functions / Cloudflare Workers），負責：
  - 安全保存和管理 App Access Token
  - 代理 Instagram/Facebook API 呼叫
  - 實作速率限制和配額監控
  - 提供簡單的 RESTful 端點給前端呼叫
- **儲存**: IndexedDB（留言資料）+ localStorage（偏好設定）

**API 整合**:
- 必須使用 Instagram Graph API 和 Facebook Graph API 作為資料來源
- 開發前需完成 Meta 開發者平台的應用程式註冊和權限申請
- 建議研究 API 文件以了解可用的端點、欄位和速率限制
- 後端代理需實作 Token 刷新機制（若 API 支援）

**前端技術選項**:
- UI 框架：React / Vue / Svelte（選擇支援快速開發和良好生態系的框架）
- 表格編輯：AG Grid / Handsontable / react-data-grid（支援大量資料和編輯功能）
- Excel 匯出：SheetJS (xlsx) / ExcelJS（支援繁體中文和複雜格式）
- 狀態管理：考慮使用 IndexedDB wrapper（如 Dexie.js）簡化資料操作
- 時間處理：date-fns / Day.js（支援時區轉換和格式化）

**後端部署選項**:
- Vercel Functions（與前端 Vercel 部署整合）
- AWS Lambda + API Gateway（彈性高、成熟）
- Cloudflare Workers（全球 CDN、低延遲）
- 選擇標準：免費額度、冷啟動時間、與前端託管的整合度
